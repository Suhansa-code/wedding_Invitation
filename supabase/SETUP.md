# Administrator Setup

1. Apply `migrations/202610270001_admin_invitations.sql`, then `migrations/202610270002_reserve_invitation_tokens.sql`, through Supabase migrations or the SQL editor, as the trusted database owner. For an existing installation with the first migration applied, apply only the second. The second migration briefly blocks invitation writes while backfilling current tokens and installing the reservation trigger in one transaction.
2. Create an administrator in Supabase Authentication. Disable public email sign-ups if they are not otherwise needed. There is intentionally no sign-up, membership-management, or password-reset endpoint in this app.
3. From the trusted SQL editor only, run `insert into public.admin_users (user_id) values ('AUTH-USER-UUID');`. Remove a row to revoke access. App users cannot write memberships, even if they are administrators.
4. Set the environment values listed in `.env.example`. Use an HTTPS `NEXT_PUBLIC_SITE_URL` for production. The secret key stays on the server and is used only to resolve one active invitation's display name. Admin operations use the publishable key, verified authentication, and RLS.
5. Configure Supabase Auth's rate limits and production email settings. Password login is rate-limited by Supabase Auth, not by process-local memory. Enable Supabase's CAPTCHA protection if appropriate for your deployment; the current UI does not implement a CAPTCHA challenge. Use a strong unique administrator password. Set appropriate network/edge limits for `/admin/login` as additional abuse protection.

Never expose the `private` schema through the Data API. Its membership helper is a security-definer function with an empty search path, owned by the migration's trusted database owner; it avoids recursive RLS on the membership table. Anonymous users have no invitation SELECT policy or table grants. Public resolution always runs on the server, bypasses caches, and selects only `display_name` for the exact active token. Tokens are bearer secrets; avoid logging invitation URLs or sending them to analytics. Automatic tokens have 192 bits of randomness. Short/custom tokens are more guessable and should not contain guest names or personal information.

The private token registry permanently reserves every token backfilled or subsequently committed on an invitation, including tokens on inactive or later-deleted invitations. Regeneration cannot reuse a previous token on the same or another invitation: inserts and token changes fail with `unique_violation` (SQLSTATE `23505`) and a generic message for reserved tokens. Unchanged-token edits remain allowed. Reservations are atomic under concurrent writes and roll back with failed transactions. The security-definer trigger has an empty search path and works for authenticated administrators without granting registry access. The registry has RLS enabled with no policies, and neither it nor the trigger function grants access to `anon`, `authenticated`, or `service_role`. Never expose, resolve, or publish retired registry values through an API, logs, or analytics. Tokens retired before this migration cannot be backfilled from current invitation rows and are not covered unless separately imported by a trusted database owner.

The invitation status column is `is_active`. Deactivating an invitation invalidates its URL. Regenerating replaces its token and invalidates the old URL; it does not reactivate an inactive invitation. Editing guest details never changes its token. Lists are paginated at 25 rows and include inactive invitations. Creating an invitation on either admin page immediately displays its guest name and canonical link with copy/open/preview controls, independently of guest-list search or pagination. Guest and display names are single-line text with a 160-character limit; control characters, line separators, and bidirectional override/isolate controls are rejected in validation and SQL. Database errors returned to the browser are sanitized.

The canonical origin is configuration, never the incoming Host header. Admin routes are dynamic, private/no-store, and noindex. Admin permission is checked on every protected loader and invitation mutation server action, in addition to RLS. Signing out clears only the caller's own session and remains available after membership revocation. The proxy refreshes session cookies and propagates Supabase SSR cache headers; it is not the authorization boundary. The public invitation route must handle resolver errors with a generic unavailable state and must not cache rendered invitation pages.

Run backend unit tests with `npm test -- tests/backend.test.ts`. To exercise real RLS, apply both migrations above, then run `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/tests/invitations_rls.sql` as the owner of a migrated local test database. This SQL test uses assertions rather than pgTAP and rolls back all fixtures. It covers anonymous/non-admin access, administrator operations, membership write denial, revocation, active/inactive resolution, input constraints, registry access denial, regeneration, retired-token rejection on inserts and updates, and unchanged-token name edits.
